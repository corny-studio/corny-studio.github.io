# vuln_watch — client infrastructure monitoring

Passive port, banner, and HTTP-security-header monitor with email alerts on change.

## Authorization

Every host in `config.json` must be one you own or have **explicit written
authorization** to test (a signed agreement, naming the exact scope). Nothing in
this tool sends exploit payloads or confirms a vulnerability is exploitable — it
connects, reads what a service already volunteers, and checks for standard
security headers. That passivity does not substitute for authorization.

## How it's organized (one script, two places it runs)

| Where | What it's for |
|---|---|
| **GitHub Actions** (`.github/workflows/scan.yml`) | The real, scheduled runner. Runs every 3 hours on GitHub's own servers — independent of any laptop being on. This is the production system. |
| **A local clone (e.g. on Kali)** | Editing `config.json`, pushing changes, and — once an alert fires — the hands-on follow-up (`nmap`, `searchsploit`) using the exact commands the alert email suggests. **Does not run its own schedule.** If a local `crontab` entry for this tool still exists, remove it with `crontab -r` — running it in two places at once means duplicate scans and duplicate client-facing emails. |

## Files

| File | Purpose |
|---|---|
| `vuln_watch.py` | The scanner. One script, no other version of this exists — if you see `vuln_watch_daemon.py` or a copy with a different findings/diff logic anywhere, it's stale; delete it. |
| `config.json` | Real targets + SMTP settings. **Never commit this to a public repo.** This repo must stay **Private**. |
| `config.example.json` | A safe template showing the structure, no real data. |
| `.github/workflows/scan.yml` | The schedule. Edit the cron line here to change frequency. |
| `state.json` | Auto-generated by the tool itself after the first run. The workflow commits it back to the repo so findings are compared run-over-run, not just within one run. Don't hand-edit it. |

## No real clients yet? Use these instead

While there's no signed scope and no real target, these are legitimate, legal
stand-ins — already in `config.example.json`, already verified live:

- **`testphp.vulnweb.com`** and **`test.acunetix.com`** — Acunetix/Invicti's own
  permanently-hosted test applications. Deliberately vulnerable, built specifically
  for security tools to scan. No authorization question at all.
- **`demo.owasp-juice.shop`** — OWASP's official public demo instance of Juice Shop,
  same purpose. Their own docs say no guaranteed uptime ("sneak-peek instance
  only"), so if it occasionally closes, that's expected, not a real finding.
- **`scanme.nmap.org`** — also sanctioned, but its own policy asks for light,
  infrequent use since it's a shared community resource. Good for one manual
  `python3 vuln_watch.py --baseline` test, not for the recurring every-3-hours
  schedule — leave it out of `config.json`'s permanent target list.

## One-time setup

1. This repo is **Private**. Keep it that way — `config.json` holds real client domains.
2. Repo → **Settings → Secrets and variables → Actions** → add:
   - `VULN_WATCH_SMTP_USER` — your sending email address
   - `VULN_WATCH_SMTP_PASS` — an app-specific password (never your real account password; regenerate it if it was ever pasted anywhere outside this one secret)
3. Edit `config.json` with real, authorized targets.
4. Repo → **Actions** tab → **vuln_watch scheduled scan** → **Run workflow** (manual trigger, confirms everything works before trusting the schedule).
5. Check your email for the "baseline established" message. If it arrives, the pipeline is confirmed working end to end.

## What changes trigger an email, and what doesn't

- A port opening or closing → reported.
- A **new** flagged issue (outdated server version, a missing security header) → reported, with a specific `nmap`/`searchsploit` follow-up command.
- An issue that was present and is now **gone** → reported as "resolved," not silence.
- Something that was already flagged last run and is **still** flagged, unchanged → **no email.** This is deliberate: re-alerting on the same unresolved finding every single run would make real alerts invisible in the noise. (This was a real bug in an earlier draft of this tool — verified fixed, with a direct regression test using real captured GitHub Pages response data.)

## Local commands (when working from a clone)

```bash
python3 -m json.tool config.json          # validate config.json after any edit
python3 vuln_watch.py --baseline          # reset comparison state after a real config change
python3 vuln_watch.py                     # run one scan by hand
git add . && git commit -m "..." && git push   # push a change so the next scheduled run uses it
```
